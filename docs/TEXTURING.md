# Texturing

> **Provenance: PORTED + DOCTRINE.** The method — art as code, structure-aware painting,
> determinism, measure-before-designing — is DOWNTIME's, and the "digital camouflage"
> lesson cost that project a whole paint pass. The 16×16 specifics and the tiling work are
> new here.
>
> This document has a **worked example with real output** in `docs/img/`, including the
> failure. Read [`ARTSTYLE.md`](ARTSTYLE.md) for *what* to draw; this is *how*.

---

## Art is code

Every texture in this project is **generated by a Python script**, not painted by hand in
an editor. This is DOWNTIME's approach and the reasons carry over intact:

- **It is reviewable in a diff.** A changed rule is a changed line. A changed PNG is an
  opaque blob nobody can review.
- **It is reproducible.** Delete every PNG and get identical bytes back.
- **The palette cannot drift**, because there is no way to type a colour.
- **Re-theming is a re-run.** Change `FAMILIES`, rebuild everything.

**16×16 is where this approach is strongest.** At 256 pixels a script is not a compromise
against hand-painting — a rule like "mortar in the gaps, highlight on the up-left rim" *is*
the drawing, expressed exactly.

### But it is not an excuse to skip looking

Generated does not mean correct. The worked example below passed the palette checker, used
exactly four legal values, and was still **wrong in a way only visible when rendered tiled**.
The script is how the pixels get placed; your eye is still the gate.

## The toolchain

| Tool | Job |
|---|---|
| `tools/colorlab.py` | sRGB ↔ CIE L\*, HSV. No colour math anywhere else. |
| `tools/pngio.py` | dependency-free PNG read/write + nearest scaling |
| `tools/paintkit.py` | painting primitives — palette access, wrap geometry, structure |
| `tools/palette_build.py` | solves the ramps → `assets/palette.json` |
| `tools/palette_check.py` | enforces the palette law; exits non-zero |
| `tools/texview.py` | **the review bench** — tiled, scaled, greyscale, icon-size |
| `tools/demo_structure.py` | the worked example below |

**No Pillow, no numpy, no pip install.** A pipeline that needs a dependency install is a
pipeline that stops running. `pngio` decodes real externally-produced PNGs (verified
against DOWNTIME's own Blender-exported textures) and round-trips byte-identically.

## `paintkit` — reach for the method, not the numbers

`paintkit.py` contains **no textures and no per-block constants**, deliberately.

> DOWNTIME's `charkit.py` holds shared mesh primitives and *contains no proportions at all*,
> because a character builder that can reach for another character's numbers will. "A doc
> telling people not to copy proportions loses to a deadline; a module that does not contain
> them does not."

Same rule. Keep the numbers in the builder; keep the method here.

```python
from paintkit import pal, Cells, h2, tdist, tdelta, solid, contour, SIZE

pal("stone", 2)          # -> (120, 125, 129). The ONLY way to get a colour.
```

`pal()` raises on an unknown family and on an out-of-range step. **A literal RGB tuple
anywhere in this repository is a bug** — see [`PALETTE.md`](PALETTE.md).

## Determinism: `random` is banned

Textures must be byte-identical across machines and runs.

A seeded PRNG is **not** sufficient: it still drifts the moment call order changes, so an
unrelated edit silently rewrites every texture after it and the diff is unreviewable. Use
`h2(x, y, seed)` — a stable hash of a lattice point. Same input, same output, forever,
regardless of what ran before it.

---

## Everything wraps

A block face is seen **tiled**. Any operation that clamps at the edge instead of wrapping
grows a lattice across every wall built from it.

```python
tdist(0, 0, 15, 0)    # -> 1.0, not 15.0. Opposite edges are NEIGHBOURS.
tdelta(0, 0, 15, 0)   # -> (-1, 0). Shortest path is across the seam.
```

Use these, not `math.hypot`. `texview` reports **edge delta** — the mean per-channel
difference between opposite edges — so wrapping is measured rather than assumed.

## Structure-aware painting

> **The single most transferable thing DOWNTIME learned, and the reason its art reads as
> painted rather than generated.**

The failure it names:

> A hash on a broad surface is **digital camouflage**. Every cluster sits where a random
> number put it, so no cluster means anything, and the result reads as generated rather
> than painted.

And the diagnosis, which is the useful half: this is **structural, not aesthetic**. A paint
function handed only a coordinate *has no idea what it is painting on*, so a hash is the
only tool it has left. The fix is not better randomness. It is **giving the painter the
structure.**

### `Cells` — the "what am I on" index

```python
cells = Cells(11, seed=3)
idx, dist, edge, (nx, ny) = cells.at(x, y)
```

- `idx` — **which** cell (so a whole stone can share a value)
- `edge` — **how near its boundary**, 0 inside → 1 at the rim
- `(nx, ny)` — **which way its interior lies**, so lighting can be directional

Now every decision can be written against structure: mortar where `edge` is high,
highlight on rims facing the light, shadow on rims facing away. **A hash survives only as a
breaker inside a zone that structure already chose.**

### Two numbers that were quietly producing noise

Both ported, both were real bugs:

- **A rim is a fixed width in the world, never a fraction of the part.** An edge band
  expressed as a fraction makes every pixel on a small face an "edge." `Cells.at` computes
  `edge` from the *gap between the two nearest sites* against a fixed 1.6 px rim, not from
  cell size.
- **Not every part gets the same treatment.** If every edge is lit, none of them is the one
  to look at. Leave a share of cells unhighlighted entirely — the example lights 45%.

## The worked example, including its failure

`tools/demo_structure.py` paints the same 16×16 stone twice, from **the same palette, the
same four values, the same pixel size**. Only the placement rule differs.

```sh
python3 tools/demo_structure.py docs/img
python3 tools/texview.py docs/img/stone_structure.png --tile 6 --scale 6
```

| | |
|---|---|
| **Hash-painted** — every pixel's value from a random number | ![hash](img/tiled_hash.png) |
| **Structure-painted** — mortar in gaps, light on up-left rims | ![structure](img/tiled_structure.png) |

Both pass `palette_check.py`. Both use four colours spanning L\* 0.180–0.701. The hash
version is digital camouflage *and* has grown a diagonal lattice from tiling.

### The failure this example went through — and it is the point

The first structure-painted version used **7 cells and a full-brightness highlight**. As a
single tile it looked correct. Tiled 6×6 it produced **a regular grid of bright dots** — the
exact pattern-tiling failure written up in `ARTSTYLE.md` §4b, committed by the person who
had just written that section.

What fixed it:

- **more, smaller cells** (7 → 11), so no single cell dominates
- **the highlight moves exactly one step** off the cell's own value, never to maximum
- **fewer lit cells** (62% → 45%)
- **a hash breaker inside the rim zone**, so the highlight is hand-painted rather than a
  clean outline

> **The single tile is the front view.** DOWNTIME's hardest-won review rule is *judge in
> rotation, always* — a model shipped with a bare strip of skull because every review was a
> front view, and the front is the view everything gets tuned in. For block textures, the
> single tile is that view. **Never judge a block from one tile.**

## Measure before you design

> At 315 texels/m a radian of face is ~47 texels and the whole mouth is twelve of them.
> Anything under ~2 texels does not survive the bake.

Same arithmetic, much smaller canvas. **One pixel is 6.25% of a block face.** A feature
under 2 px will not survive mipmapping and will shimmer at distance.

Count the pixels your detail will occupy *before* drawing it. If the answer is 1, it is not
a detail, it is noise.

---

## Values are stepped, never blended

No gradients. No anti-aliasing. No interpolation between palette entries — an interpolated
colour is **off-palette by definition** and `palette_check.py` will say so.

Use `step_shade(family, base, ±1)` to move along a ramp. Three to five values per texture.

**Dithering** — a checker of two adjacent ramp steps — is the only legitimate way to imply
an intermediate value, and it must be placed from structure like everything else. A dither
scattered by hash is digital camouflage with extra steps.

## The review bench

```sh
python3 tools/texview.py t.png                      # 8x8 tiled at 6x -- the default, on purpose
python3 tools/texview.py t.png --tile 4 --scale 12
python3 tools/texview.py t.png --icon               # 16px, what a hotbar shows
python3 tools/texview.py t.png --grey               # the desaturation test
python3 tools/texview.py a.png b.png --sheet out.png
```

It prints, every time: dimensions, **colour count** (warns above 8), **L\* range**, and
**edge delta** for wrap quality. Transparency is composited over a checkerboard so alpha is
visible rather than guessed.

**The default is tiled, not single.** A bench whose easiest invocation shows the misleading
view is a bench that will mislead you.

### Naming convention — it is load-bearing

`texview` writes `<base>_view.png` and `<base>_grey.png`; contact sheets are `sheet_*`;
tiled renders committed for docs are `tiled_*`. **`palette_check.py` skips exactly these
patterns**, because a greyscale render is off-palette by construction.

Do not override these names with `--out` when writing into a checked tree. Verified both
ways: identical bytes are skipped under a review name and caught under an asset name — the
skip is a naming rule, not a hole.

## Where textures live

**VERIFIED against 26.2.0.67.** These are the paths this repo ships from and
`tools/registry_check.py` resolves on every push — every block, item and entity texture
below is one CI proves a live server and a model reference can find. The item-model
layout that changed during the 1.21 line is the **two-file split**, settled in
[`MODELS.md`](MODELS.md): a definition under `assets/<ns>/items/` and, for flat items
only, a model under `assets/<ns>/models/item/`.

```
src/main/resources/assets/<mod_id>/
  textures/
    block/     16x16, tiling, no contour
    item/      16x16, contoured
    entity/    per-model atlas (64x64 / 64x32 conventions)
    gui/
  models/
    block/
    item/
  blockstates/
```

Point the checker at the tree root and it walks everything:

```sh
python3 tools/palette_check.py --textures src/main/resources/assets
```

## The loop

1. Write the rule in a builder script.
2. Run it.
3. `palette_check.py` — machine rules.
4. `texview --tile 8` — **look at it as a wall.**
5. `texview --icon` for items — **look at it at 16 px.**
6. `texview --grey` — does the composition survive desaturation?
7. In-game beside the nearest vanilla block, at play distance.

Steps 1–6 cost seconds. Step 7 is the only one that is ever conclusive, and it is the one
DOWNTIME's owner reserved for themselves — *"the real gate is still a screenshot."*
